RiftLinux is a modified Monado, specialized for full Oculus Rift CV1 support: the headset, its Constellation sensors
and its Touch controllers on Linux, in SteamVR and in OpenXR applications, from one package. No Windows, no Oculus
software, no Meta account.

This pre-release adds panel uniformity, a steadier supersampled picture and a set of safety fixes. 0.1.5 stays the
current release until these changes are confirmed on more systems: reports are very welcome.

## New

- **Panel uniformity.** Every CV1 panel is a little uneven, which shows most in dark grey scenes. RiftLinux now evens
  out both panels with your headset's own factory calibration, as the Oculus software does on Windows. Switch it on in
  the Rift tab (*Picture*, *Panel uniformity*) or with `riftlinux-setup uniformity on`. The first time, your headset's
  factory measurement is downloaded from Meta (the request carries the headset's serial number; no Meta account is
  used) and RiftLinux builds the calibration from it. It is off by default and switches at once. It works in
  direct mode (the default in SteamVR) and in RiftLinux's own runtime. `riftlinux-setup uniformity strength` and
  `near-black` tune it, and a calibration from a Windows install can be imported with
  `riftlinux-setup uniformity import`.

## Fixed

- **Text and fine lines no longer shimmer with a render scale above 100 %.** The larger picture is now filtered down
  to the panel over each pixel's whole area, in SteamVR and in RiftLinux's own runtime, for games and for windows such
  as a VR desktop's.
- **The headset is switched fully off when SteamVR or RiftLinux's runtime quits:** display, headphones and tracking
  LEDs. Only the display was switched off before.
- **Safer with faulty or malicious USB devices.** Data from the headset, the sensors and the controllers is checked
  before it is used: lengths and sizes in the sensors' video, their JPEG pictures on USB 2, the sensors' camera
  calibration, the headset's LED model and controller serial numbers can no longer make the driver write outside its
  memory.
- **Built with the protections distributions use for their own packages.** The driver and the runtime now have
  stack protection, glibc's checked memory and string functions, and full RELRO.
- **`riftlinux-setup`'s repairs that need root are safe with any folder or path names**, and the udev rules it writes
  without the package's rules file are correct.
- **The packages carry the licence texts** of RiftLinux and of every library linked in.

## Tested on

- Panel uniformity: the calibration RiftLinux builds from the factory measurement, compared in the headset with the
  one the Oculus software prepares on Windows: no difference to the eye.
- Panel uniformity's first start on a system without a calibration (Ubuntu 25.04): the factory measurement downloaded,
  the calibration built, and a calibration that appears while the runtime runs taken up live, without a pause.
- Supersampling: SteamVR at 165 % and 200 %, and a VR desktop's windows at 200 %, in the headset.
- RiftLinux's own runtime stopped with an application connected (one that ends when asked, one that doesn't answer,
  one with no session): it stops cleanly each time, and the headset's display, headphones and LEDs are off afterwards.
- The sensors' video and camera calibration with the new checks: both sensors stream and their calibration is read.
- SteamVR with this release's driver (Ubuntu 25.04): the headset and both Touch controllers up, the Rift tab with its
  Panel uniformity switch, uniformity switched on and off while SteamVR ran, and a clean stop with the headset's
  display, headphones and LEDs off afterwards.
- The hardened build: SteamVR and RiftLinux's own runtime started and stopped with it on Ubuntu 25.04 (uniformity on,
  an application connected), and the runtime starts on every system of the package test.
- CachyOS (KDE Plasma 6.8, Wayland) with NVIDIA 615, and Ubuntu 25.04 (GNOME 48, Wayland) with NVIDIA 580.
- The packages are installed and checked in clean Ubuntu 22.04, 24.04 and 26.04, Debian 12 and 13, Fedora 43 and 44,
  and Arch systems.
- Not tested here: AMD and Intel graphics for this release's changes.
- x86-64 computers only.

## Install

Download the package for your distribution and `SHA256SUMS` below, check them with
`sha256sum --ignore-missing -c SHA256SUMS`, and install. Upgrading from an earlier version is the same command:

```bash
sudo apt install ./riftlinux_0.1.6_amd64.deb                  # Debian, Ubuntu, Linux Mint, Pop!_OS
sudo pacman -U riftlinux-0.1.6-1-x86_64.pkg.tar.zst           # Arch, CachyOS, EndeavourOS, Manjaro
sudo dnf install ./riftlinux-0.1.6-1.x86_64.rpm               # Fedora
tar xf riftlinux-0.1.6-x86_64.tar.gz && sudo ./riftlinux-0.1.6-x86_64/install.sh   # any other distribution
```

On Arch and its relatives, `riftlinux-bin` in the AUR has this version too.

Then restart Steam once (Steam, Exit, and start it again). Steam loads the part that starts SteamVR when it starts, so
it only picks up the new version after a restart. The [user guide](https://github.com/AIIX/RiftLinux/blob/main/docs/README.md)
walks you through the first start, and the [settings guide](https://github.com/AIIX/RiftLinux/blob/main/docs/settings.md)
lists every setting.

## Known issues

- With GE-Proton installed and the headset unplugged, SteamVR can start over and over as Steam starts, with its
  "headset not found" message ([#8](https://github.com/AIIX/RiftLinux/issues/8)). Steam runs its graphics driver
  check through every GE-Proton build installed; through GE-Proton that check doesn't finish and keeps starting
  SteamVR until Steam gives up on it. Moving the GE-Proton builds out of Steam's `compatibilitytools.d` folder stops
  it, and with the headset plugged in RiftLinux quits that SteamVR again.
- A VR game started from Steam while SteamVR isn't running opens on the monitor, because Steam on Linux doesn't start
  SteamVR for it. Put the headset on first (SteamVR then starts), or start SteamVR from Steam and then the game.
- Steam's client can crash when a flat (non-VR) game opens a window while SteamVR is running. That's a Valve bug, not
  this driver ([SteamVR for Linux #963](https://github.com/ValveSoftware/SteamVR-for-Linux/issues/963) is the same
  crash, reported for the Desktop tab).
- SteamVR's compositor can crash as SteamVR quits, after the session is over. It's harmless, and the exit code is
  SteamVR's own ([SteamVR for Linux #990](https://github.com/ValveSoftware/SteamVR-for-Linux/issues/990) is the same
  crash with Valve's own streaming driver).
- SteamVR's compositor sometimes doesn't start on the first try (a freeze in SteamVR's own startup). SteamVR tries
  again, and SteamVR Home shows up later than usual. Once SteamVR quits, RiftLinux ends the leftover copy of SteamVR's
  server from the failed try, so the next start isn't blocked.
- Steam asks some questions before a game's first start on the monitor, not in the headset. If a game doesn't start
  from inside VR, take the headset off and answer them there.
- SteamVR's Desktop tab is empty on Linux
  ([SteamVR for Linux #693](https://github.com/ValveSoftware/SteamVR-for-Linux/issues/693)). WayVR shows the desktop
  as an overlay.
- With NVIDIA on Wayland and a VRR monitor, the headset's picture can tear unless VRR is hidden from the driver
  (NVIDIA's bug, [open-gpu-kernel-modules #992](https://github.com/NVIDIA/open-gpu-kernel-modules/issues/992)). Run
  `riftlinux-setup nvidia-vrr conceal`.
- NVIDIA's 615 driver keeps a little memory each time a program sends work to the graphics card and never gives it
  back, in every OpenGL and Vulkan program. You notice it in programs that run for a long time. The
  [troubleshooting page](https://github.com/AIIX/RiftLinux/blob/main/docs/troubleshooting.md) names the workaround
  from NVIDIA's forum (an undocumented driver setting). RiftLinux doesn't set it for you.
- With HDR on, GNOME can leave the desktop's colours washed out when the headset connects or disconnects. Switching
  HDR off and on again in GNOME's settings fixes it (likely
  [mutter #5083](https://gitlab.gnome.org/GNOME/mutter/-/work_items/5083), fixed for GNOME 51).

The README's Known issues section has the full list, including app issues under Proton.

## Reporting a problem

Open an issue with the bug form and add the output of `riftlinux-setup --json check`, SteamVR's log
(`~/.local/share/Steam/logs/vrserver.txt`) and the driver's own log (`~/.steam/steam/logs/vrstartup-linux.txt`). Say
which GPU and driver you have.

For a tracking problem, record a session. Run `riftlinux-setup record on`, start SteamVR and do whatever shows the
problem, then attach the recording from `~/.cache/riftlinux` and SteamVR's startup log
(`~/.steam/steam/logs/vrstartup-linux.txt`). Turn it off afterwards with `riftlinux-setup record off`. For a
controller problem, also add the output of `riftlinux-setup controller-alignment status`.
